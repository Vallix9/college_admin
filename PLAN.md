# План доработки проекта College Admin

## Исходные решения

- **Объём:** полная доработка + полноценный журнал успеваемости + личный кабинет студента.
- **Окружение:** `venv`, зависимости строго из `requirements.txt`.
- **Структуру файлов не меняем:** роуты в `app/routes.py`, модели в `app/models.py`,
  утилиты в `app/utils.py`. Новые таблицы и роуты добавляются в те же файлы.
- **Данные:** сид + админ, пароль из `.env`.
- **Git:** коммит в `main` + push в `origin` после каждой фазы.

---

# Главная цель 1: журнал успеваемости (аналог дневник.ру)

Журнал = сетка «студенты × даты занятий» с оценками, пропусками, итогами за период,
двумя режимами просмотра и разграничением прав «преподаватель / администратор».

| Элемент | Решение |
|---|---|
| Сетка журнала с оценками | Да, ядро |
| Пропуски с причинами | Да (болезнь / уважительная / неуважительная) |
| Учебные периоды и итоги | Да (четверть/семестр + итоговая оценка) |
| Расписание занятий | Да (день недели, пара, предмет, группа, преподаватель) |
| Темы уроков и домашние задания | Нет |
| Режим 1: группа + предмет + период (сетка по датам) | Да |
| Режим 2: сводная по всем предметам группы | Да, переключение на странице |
| Подтверждение удаления | Да |
| Редактирование оценок с записью в историю | Да |
| Запрет выставления задним числом | Нет |
| Показывать автора в ячейке | Нет |

# Главная цель 2: учётные записи и личный кабинет студента

Студент входит по номеру зачётки и паролю, видит свои оценки, пропуски и оценки
одногруппников, может сменить пароль.

| Элемент | Решение |
|---|---|
| Форма входа | **Одна общая** для сотрудников и студентов (по логину или по номеру зачётки) |
| Первичный пароль | **Вручную в карточке** ИЛИ **генерация**, ИЛИ **массовая выдача на группу** с печатной таблицей |
| Смена пароля студентом | **По желанию**, в любой момент из кабинета |
| Видит студент | свои оценки и средний балл, свои пропуски, оценки одногруппников своей группы |
| Не видит студент | рейтинг группы, средний балл группы, чужие пароли, другие группы, данные сотрудников |
| Средний балл по предмету за семестр | **Свой** |
| Комментарии преподавателя к оценкам | Нет |
| Экспорт своих оценок | Нет |
| История изменений пароля для админа | Да (`password_changed_at`) |

# Правила работы

1. Фазы строго по порядку: фаза не закрыта, пока не пройдена её контрольная точка.
2. После каждой фазы — коммит в `main` и push в `origin`.
3. Перед крупным изменением БД — копия `college.db` в `backups/`.
4. Комментарии в код — только там, где логика неочевидна.
5. Новую функциональность сначала делаем рабочей «в коде», потом сверяем с шаблоном.
6. Ничего не удаляем, пока новая реализация не проверена.
7. Каждая страница личного кабинета проверяется на двух ролях: студент и админ.

### Решения фазы 9

- Отметка только по состоявшемуся занятию: `LessonDate` должен существовать
  для этой группы и предмета, дата не позже сегодняшней. Иначе можно было бы
  отметить пропуск на любую дату периода, включая выходной, и сводка
  разошлась бы с расписанием.
- `subject_id IS NULL` — это «отсутствовал весь день», зачёт идёт по всем
  парам дня (`AttendanceRecord.hours_count`). Такой вариант есть только у
  администратора: он задевает чужие предметы, и преподаватель не должен
  решать за коллег, кто отсутствовал. Преподаватель отмечает только свой
  предмет; чужой даёт 403.
- Повторная отметка на то же занятие не создаёт вторую запись — предупреждение
  и предложение исправить причину.
- Массовая отметка по умолчанию пропускает тех, у кого за этот день есть
  оценка: человек с оценкой явно был, и пропуск рядом с ней выглядит как
  ошибка преподавателя. Флаг «не отмечать тех, у кого есть оценка» снимаемый.
- Дашборд ранжирует лидеров по **числу дней** пропусков, а не по числу
  записей: иначе студент, сидящий на парах по понедельникам, всегда был бы
  первым в списке.
- Связи в списках отметок грузятся через `joinedload` (студент, предмет,
  автор), иначе на каждую отметку уходит отдельный SELECT.
- Скрытые поля форм приводятся к `int`: строка «2» из запроса не равна целому
  2 из базы, и проверка «студент из этой группы» всегда давала бы ложь.
- Значение 0 в списке предметов — «весь день», поэтому для `subject_id`
  используется `InputRequired`, а не `DataRequired`: тот считает 0 пустым
  полем и отверг бы вариант всегда.
- Удаление пропуска не трогает оценки за это занятие; истории правок у пропусков
  нет, причина меняется через `attendance_edit` с записью в журнал событий.
- Экспорт пропусков и свод по группе с пропусками остаются за Фазой 10
  (пункты 10.2–10.4).

### Решения фазы 10

- `PeriodResult` — отдельная сущность, а не колонка в `Grade`: итог относится
  к периоду, а не к занятию. Уникальность по `(student, предмет, период)`
  запрещает две записи на одну позицию ведомости.
- Рекомендация по среднему: `4.5 → 5`, `3.75 → 4`, `2.5 → 3`, ниже `2` — `2`.
  Пороги в `FINAL_GRADE_THRESHOLDS` и применяются и на экране, и при сохранении,
  поэтому подмена подсказки в форме не обходит правило.
- Шкала «зачёт/незачет» не переводится в числа: среднее по ней бессмысленно,
  рекомендация возвращает исходную букву.
- Обоснование обязательно, когда выставленный итог отличается от рекомендации.
  Сервер пересчитывает рекомендацию сам, а не доверяет скрытому полю формы.
  Пустое значение итога снимает его — это отдельный сценарий без обоснования.
- Рекомендация не может выставить `5` при среднем ниже `4.5`, но преподаватель
  вправе поставить `5` с обоснованием: автоматика подсказывает, решает человек.
- Качество — доля `4` и `5`, успеваемость — доля `3`, `4`, `5`. «Двойка» не
  попадает ни в одну из долей, поэтому в процентах она и не видна: это доля
  хороших оценок от всех оценок, а не доля сдал.
- Пропуски считаются по датам периода, а не по записям: один день прогула —
  это одна строка `AttendanceRecord`, сколько бы пар в этот день ни было.
- Права совпадают с `journal`: администратор — все предметы, преподаватель —
  свои, чужой предмет даёт 403, а не подмену на доступный.
- Excel строится из того же `ctx`, что и экран, через
  `journal_export_frames()`. Отдельная сборка данных для экспорта разошлась
  бы с интерфейсом, а расхождение заметят первым на печати.
- CSV журнала всегда в режиме дат: заголовок содержит «Дата», а не идентификатор
  предмета, поэтому в режиме предметов колонки нечитаемы.
- Имя файла собирается из понятных подписей; строки с `/` и кириллицей
  приводит `openpyxl`, поэтому безопасное имя — требование, а не аккуратность.
- `@media print` скрывает через явный класс `no-print` в `base.html`, а не
  через `header`, `footer` и селекторы по тегу: разметка страницы меняется
  вместе с вёрсткой, и версия для печати отстаёт от экрана.

### Решения фазы 11

- Логин ученической записи не вводится: он равен номеру зачётки. Дублировать
  его в форме — значит разрешить расхождение, при котором в журнале входов
  одно имя, а в ведомости другое. Форма только задаёт пароль.
- Сравнение логинов **без учёта регистра и в общей таблице `User`**. Проверка
  только среди студентов пропустила бы номер зачётки `admin`: карточка
  сохранилась бы, а войти студент не смог бы.
- Сравнение выполняется на Python, а не через `lower()` в SQLite: SQLite
  понимает в `lower()` только латиницу, а Python — ещё и кириллицу, поэтому
  запрос не нашёл бы «ДБ-01» по `дб-01`, и человек с верным паролем получил бы
  «неверный логин». Сначала точное совпадение, потом перебор — записей единицы,
  а перебор случается только когда точного совпадения нет.
- Вход идёт через `find_user_by_login()` по той же причине: строгий поиск дал бы
  «неверный логин» на верном пароле, и администратору пришлось бы объяснять это
  студенту, который просто не переключил клавиатуру.
- Флаг `User.password_temporary` отвечает на вопрос «менял ли человек пароль
  сам». Сравнивать `password_changed_at` с `created_at` нельзя: `set_password`
  вызывается и при выдаче, и при смене, и времена совпадут до секунды. Флаг
  ставится при выдаче и снимается в `/my/password`.
- Временный пароль состоит из **читаемых** символов без `0/O` и `1/l/I`.
  Из `generate_password` для раздачи не годится: с распечатанной ведомости
  студент раз за разом вводит не тот пароль и приходит к администратору с
  ложным «пароль не подходит».
- Ведомость с паролями сохраняется файлом в `exports/` под случайным именем и
  отдаётся только администратору. В журнал событий пишется число выданных
  записей, но не сами пароли: журнал читают при разборе инцидентов.
- Удаление ученической записи снимает связь `Student.user_id`, но оставляет
  самого студента вместе с оценками. Забытый пароль не должен обнулять историю
  успеваемости, а запись создаётся заново одной кнопкой.
- Удаление не выдаёт пароль заново молча: это отдельное действие. Иначе кнопка
  «выдать всем» сбрасывала бы чужие пароли, и студент узнал бы об этом на
  следующей паре.

- `user_id` в журнале объявлен с `ondelete='SET NULL'`. Обычное ограничение
  превращало бы удаление сотрудника в ошибку целостности, как только база
  начнёт проверять внешние ключи: запись-то удалять нельзя.
- Тесты оставляли в журнале записи о своих входах и выгрузках, а `phase13`
  проверял «запись появилась» по всей таблице — из-за этого пропущенный вызов
  `log_audit()` мог остаться незамеченным. Теперь:
  - каждый фазовый тест запоминает последний `id` журнала и удаляет записи
    выше него (то же в `roles_test` и `smoke_test`);
  - `phase13_test` считает только записи текущего прогона;
  - каждая операция сначала проверяется на **принятие** запроса: отказ
    проверкой формы не доходит до `log_audit()`, и «запись есть» ничего не
    значит.
- Именно так нашлась ошибка в самом тесте: массовая отметка пропусков
  отправляла причину `sick`, которой нет среди `REASONS`, и отвергалась
  проверкой формы — то есть операция не была проверена вовсе.
